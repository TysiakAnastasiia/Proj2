# Архітектура BookSwap

## Структура проекту

BookSwap розділено на логічні шари для забезпечення чистоти коду та тестованості:

- `backend/app/models/` — доменні моделі та сутності
- `backend/app/repositories/` — інтерфейси доступу до даних та реалізації
- `backend/app/services/` — бізнес-логіка та правила роботи додатку
- `backend/app/api/` — FastAPI маршрути та обробка HTTP-запитів
- `backend/app/core/` — конфігурація, безпека, патерни та інфраструктура
- `backend/tests/` — юніт та інтеграційні тести

## Шари архітектури

### Модель (Model)

- Зберігає бізнес-дані
- Визначає структуру об'єктів
- Мінімізує залежності

### Репозиторій (Repository)

- Інкапсулює доступ до даних
- Використовує абстракції для наступності
- Підтримує in-memory реалізацію та реальні драйвери

### Сервіс (Service)

- Реалізує бізнес-правила
- Оркеструє виклики між репозиторіями
- Працює з подіями та правилами валідації

### API

- Приймає HTTP запити
- Валідує вхідні дані
- Виконує авторизацію та аутентифікацію
- Повертає відповіді у форматі JSON

## Використані патерни

### Observer

- Використовується для системи сповіщень
- Дозволяє декільком підписникам реагувати на події

### Strategy

- Використовується для варіантів алгоритмів штрафів, рекомендацій та фільтрацій
- Забезпечує можливість підмінювати логіку без зміни коду клієнта

### Singleton

- Використовується для глобальної конфігурації та управління ресурсами

### Factory

- Використовується для створення репозиторіїв та сервісів
- Дозволяє легко підмінювати реалізації у тестах

## In-memory архітектура

Для розробки проект використовує in-memory сховище:

- Репозиторії оперують словниками та списками
- Відсутні зовнішні бази даних у тестовому режимі
- Можливість легкої заміни на реальну БД через DI

## SOLID

- Відокремлені інтерфейси та реалізації
- Окремі сервіси для кожного типу бізнес-логіки
- Одна відповідальність на модуль
- Залежності інвертовано через фабрики та DI
